# Установка методологии SDD в вашего агента — `sdd install`

> Русский · [English](installing-rules.md)

`sdd install` делает `agent-sdd` **точкой распространения методологии
SDD**. CLI поставляет набор правил под `rules/`; `install` копирует его
в конфигурацию вашего AI-агента для программирования, чтобы в любом
открываемом проекте агент следовал дисциплине — читал спецификацию через
`sdd record`, держал код и спецификацию в синхронизации, никогда не
самоутверждался, прогонял гейты.

Наличия бинарника `sdd` самого по себе недостаточно: бинарник *принуждает*
к методу, но агент должен *знать* метод. `sdd install` — это то, что его
этому обучает.

---

## Что распространяется

Набор артефактов управляется данными из [`rules/manifest.json`](../rules/manifest.json)
(никогда не захардкожен), поэтому он остаётся синхронным с тем, что
поставляет пакет. По состоянию на v1.4.0 это:

| Вид | Источник | Устанавливается как | Назначение |
|------|--------|----------|---------|
| context | `spec-driven-development.md` | `@import`-ируемое / упоминаемое правило | Сжатое правило SDD, всегда в контексте агента. |
| context | `workflow-sdd.md` | правило | Дополненный SDD рабочий процесс разработки (spec → lint → implement → ready). |
| context | `tdd-sdd.md` | правило | Откуда берётся Red; маркеры `@covers`; runtime-state миграции. |
| context | `sdd-cli-usage.md` | правило | Отображение фаза → команда и операционные правила для CLI. |
| context | `review-sdd.md` | правило | Дополнение к чек-листу самопроверки для SDD. |
| skill | `skills/spec-driven-development/SKILL.md` | скилл по требованию | Полный справочник с таблицами и обоснованиями, загружается при необходимости. |
| reference | `enforcement_registry.md` | справочный файл | Отображение requirement → enforcement-class → executor (`ENF-*`). |
| data | `skills/…/data/weasel-words.json` | файл данных | Канонический список weasel-слов, используемый при рассуждениях линтера. |
| hook | `hooks/sdd-lint-reminder.sh` | хук `PreToolUse` (Claude) | Напоминает агенту запустить `sdd lint` после редактирования файла спецификации. |
| hook | `hooks/sdd-spec-read-guard.sh` | хук `PreToolUse` (Claude) | Запрещает `Read`/`cat`/`grep` для `spec/*.md`, вынуждая использовать `sdd record`. |

Контекстные правила небольшие и всегда включены; скилл — это глубокое
руководство, подтягиваемое по требованию; два хука — это *механическая*
половина, которая держит Claude-агента честным даже когда он забывает
правило.

## Цели

```sh
sdd install claude       # ~/.claude
sdd install codex        # ~/.codex
sdd install all          # оба
```

### `claude`

- Контекстные правила копируются в `~/.claude/sdd/` и подтягиваются в
  **управляемый блок** в `~/.claude/CLAUDE.md` через `@import`.
- Полный справочник устанавливается как **скилл по требованию** по пути
  `~/.claude/skills/spec-driven-development/SKILL.md`.
- Два хука `PreToolUse` объединяются в `~/.claude/settings.json`:
  - **напоминание о линте** — неблокирующее; подталкивает агента запустить
    `sdd lint` после того, как он отредактировал файл спецификации;
  - **сторож чтения спецификации** — *блокирующий*; запрещает читать
    `spec/*.md` напрямую в любом проекте, несущем `.sdd/config.json`, чтобы
    агент навигировал по спецификации через `sdd record list` / `get`
    вместо загрузки всего файла в контекст.

### `codex`

- Каждое правило копируется в `~/.codex/sdd/` и перечисляется в управляемом
  блоке в `~/.codex/AGENTS.md`.
- У Codex нет механизма `@import` и хостинга хуков, поэтому хуки
  **отмечаются как пропущенные** — правила всё равно применяются, но два
  принуждающих хука доступны только для Claude.

## Область пользователя против области проекта

```sh
sdd install claude                 # --scope user   (по умолчанию)
sdd install all --scope project    # в ЭТОТ репозиторий
```

- **`user`** (по умолчанию) — пишет под корни домашних каталогов агентов:
  `~/.claude` и `~/.codex`. Это режим «настрой один раз, выигрывает каждый
  проект». `$SDD_INSTALL_HOME` переопределяет корень домашнего каталога
  (полезно для тестирования).
- **`project`** — пишет конфигурацию агента в **текущий репозиторий**,
  чтобы команда могла закоммитить настройку SDD и поделиться ею:
  - `./CLAUDE.md` и `./AGENTS.md` в корне репозитория;
  - правила, скиллы и `settings.json` под `./.claude/**` и `./.codex/**`.

  Команды хуков в `settings.json` области проекта используют
  `$CLAUDE_PROJECT_DIR/.claude/sdd/…` (не абсолютные пути), поэтому
  закоммиченный `settings.json` переносим между машинами и чекаутами.

Область проекта пишет **только** этот набор конфигурации агента. Она
никогда не трогает `spec/*.md`, `.sdd/config.json`, `.git` или ваш
исходный код. Это жёсткая граница (`INV-016` / `POL-003` / `POL-001`) —
`install` *не* является командой скаффолдинга и не создаст спецификацию
или конфиг за вас.

## Свойства безопасности

- **Планируй-затем-применяй.** Если какой-либо упакованный файл-источник
  отсутствует, `install` прерывается *до записи чего-либо* (exit 1,
  `artifact-missing` / `manifest-missing` / `manifest-invalid`). Вы никогда
  не получите наполовину записанный конфиг.
- **Идемпотентность.** Управляемые блоки заменяются на месте; записи хуков
  дедуплицируются по matcher + command; ранее существовавшие
  пользовательские хуки сохраняются. Запуск дважды — это no-op сверх
  обновления управляемого содержимого.
- **Ограниченные записи.** При `--scope user` пишет только внутри корней
  домашних каталогов агентов; при `--scope project` — только внутри набора
  конфигурации агента в репозитории. Это *единственная* команда, которой
  разрешено писать вне репозитория, и даже тогда только в эти корни.

## Предпросмотр и машинный вывод

```sh
sdd install all --dry-run          # показать запланированные файловые операции, ничего не писать
sdd install claude --format=json   # стабильный JSON-конверт для скриптов
```

`--dry-run` печатает ровно то, какие файлы будут записаны, какие
управляемые блоки заменены и какие хуки объединены — запустите его первым,
если хотите увидеть радиус поражения, прежде чем на это соглашаться.

### Коды выхода

| Exit | Причина | Значение |
|------|--------|---------|
| 0 | — | Установка (или план `--dry-run`) завершена. |
| 1 | `manifest-missing` / `manifest-invalid` / `artifact-missing` | Упакованный файл правил или манифест не удалось прочитать; ничего не записано. |
| 2 | — | Ошибка argv (отсутствующая/неизвестная цель, неизвестный флаг). |

## После установки

Откройте вашим агентом любой проект, несущий `.sdd/config.json`. Вы должны
увидеть:

- правила SDD во всегда-включённом контексте агента;
- (Claude) отказ, когда агент пытается сделать `Read` / `cat` / `grep`
  для `spec/*.md`, перенаправляющий его к `sdd record`;
- (Claude) напоминание запустить `sdd lint` после того, как агент
  отредактировал файл спецификации;
- скилл `spec-driven-development`, доступный агенту для подтягивания
  полного справочника по требованию.

Чтобы обновить правила после обновления `agent-sdd`, просто запустите
`sdd install` снова — она идемпотентна и обновляет управляемые блоки на
месте.
